## 撤回的旧结论

旧版把两步时长相加后当成 `submit_fact_selection` 时点，再用它计算“提交至可见约 0.4–2.6 秒”。当前没有同一请求下的提交落库时间，**这三个间隔不可计算**。平台步骤时长说明模型流程占用了较多时间，但不能把剩余时间全部归因到模型，也不能排除平台事件、流关闭、停止请求或后端校验保存的等待。

`submit_fact_selection` 保存的是候选事实选择。随后客户端需收到可触发可信检查的 `execution_logs` / `execution_result` 事件（或流正常完成），适配器还要 finalize，API 再生成并校验正文、保存事件，之后页面才能显示。因此“提交即获准展示、提交后立即渲染”不符合实际调用链。

规则模拟器的 16–33 毫秒样本跳过了真实 Nexent/MCP/SSE 路径，不能用它证明真实模式的“授权后链路无可去除等待”。本轮新增 `test_answer_waits_for_platform_wakeup_validation_and_save` 三个可控实验：分别在提交前、提交后尚未发送完成事件、正文校验后暂停。三处暂停均阻止请求返回，事件尚未保存；释放后答案保存一致，同一请求重试仅重放一次。现有 `test_deadline_cancels_submitted_turn_and_same_request_retries_once` 则验证提交后流停滞可超时并取消，不能提前显示未保存答案。这些是隔离工程证据，不是新的真实时延结果。

## 已落地的关联观测点（本轮，语义已更正）

服务端 `/api/sessions/{id}/ask` 响应 `timing.stages` 与持久事件 `result.server_stage_ms` 按同一 `request_id` 记录 API 进程内的 monotonic 毫秒：`request_entry`（处理器开始）、`classified`（分类完成）、`adapter_returned`（患者适配器返回，即模型运行与回合 finalize 结束）、`validated`（正文授权校验完成）、`saved`（会话保存完成）。持久事件只快照到 `validated`，`saved` 仅在返回前补齐。适配器 `trace` 另有 `trusted_completion_ms`（本进程**首次观察到**本地回合已提交的时刻）与 `finalize_ms`（finalize 完成）。以上只记时点/状态，不含令牌、密钥或模型原文，由 `tests/test_integration.py::test_ask_records_request_scoped_stage_and_trace_timestamps` 锁定。

**边界（撤回过强表述）**：这些字段不能支撑「提交落库到绘制全链路逐段拆开」。

- `adapter_returned` 是适配器返回，不是模型 `submit_fact_selection` 落库；落库发生在独立 MCP 进程，其时间是 `turn_calls.at`（墙钟 `time.time()`），与 API 进程的 monotonic 不在同一时钟、不能相减。
- `trusted_completion_ms` 是「首次观察到提交」的检测时刻，同样不是实际落库时刻。
- `saved` 是保存完成；实际响应发出、浏览器收到响应头、DOM 更新、双 rAF 分别是不同口径，浏览器端由 `postT/visibleT/paintT` 记录，双 rAF 仍是显示时点估算而非物理绘制实测。
- 服务器单调时点与浏览器时间起点不同，不能直接相减定位单向网络耗时。

因此本轮只补齐了 API 进程内的阶段观测与「首次观察到提交」的检测时刻；真实平台复测仍需新预算，并在 MCP 进程补 `submit_fact_selection` 落库的单调/墙钟时点后才能逐段拆解提交之后的链路。

## 浏览器端到端可控等待（本轮已完成，零模型调用）

`web/e2e/controlled-wait.mjs` + `web/e2e/ask_stack.py` 用假 Nexent/真实后端/MCP/临时库 + 真实浏览器，在三个位置注入事件屏障：提交前（`before_submission`）、提交后尚未发完成事件（`after_submission`）、正文授权校验后（`after_validation`），外加一个平台停滞超时场景。假 Nexent 现在**先建立 SSE 流并发出 thinking 事件、再驱动可信 MCP 提交**，因此「提交后」屏障发生在响应头/流已建立、可信提交已完成、仅完成事件被暂停的位置，更接近真实平台。结果见 [2026-11-27-controlled-wait.json](2026-11-27-controlled-wait.json)。

每轮记录同一请求的 `request_id`、服务端阶段（API 进程 monotonic）、适配器 `trace`（`trusted_completion_ms`/`finalize_ms`/`first_event_ms` 等）、浏览器点击/响应/DOM/双 rAF 估算、屏障到达/释放时刻，并标注各自计时起点（浏览器 `performance.now()`、API 进程 monotonic、驱动端 `Date.now()` 墙钟，不能跨时钟相减）。三处暂停期间均「请求未完成、无正文、无保存」；释放后核对 HTTP 状态、API 正文、DOM 正文、持久正文一致；并用同一 `request_id` 直接重放，核对平台运行次数与持久事件数均不增加；停滞超时场景核对失败不显示未完成答案、不保存。

这些只能证明：三处受控暂停期间学生未提前看到正文、服务端未提前保存训练事件；释放后流程完成、保存一致。**不能据此推出「没有可单独去除的人工等待」或「8–10 秒全部来自模型流程自身」**——真实平台各阶段耗时与可优化等待仍未完整定位。至少还有这些边界：

- 假平台在同一进程内通过可信 MCP 提交，`submit_fact_selection` 落库仍无独立（MCP 进程）单调记录；`trusted_completion_ms` 是「首次观察到提交」的检测时刻，不是实际落库时刻。
- 平台步骤时长之和（7.3–7.9 秒）只是 runtime 汇总时长，不是提交落库时刻，不能与浏览器时点相减或当作提交/授权时刻。
- 不同进程/主机、不同起点的 monotonic 值不能直接相减；补墙钟也不会自动消除时钟同步与采集误差。
- 双 rAF 只是显示估算，不是物理绘制实测。

因此「缩短首字只能换模型或改协议」没有证据支持：在补齐 MCP 进程提交落库时点、并区分响应头等待/事件唤醒/流结束等待之前，不能排除其他可优化的等待，也不能排除平台事件、流关闭、停止请求或后端校验保存的等待。
